# 事务消息回查与重发

## 消息、事务和确认

1. 沿用当前按 `ORDER_BUILD:` 加 traceId 派生的稳定 eventId。消息 Key 是 eventId，标签是 `ORDER_BUILD`，正文保存 `{"traceId":"..."}`。正式 Topic 由部署配置，在隔离 Broker 验证事务和普通发送的 Topic 类型与订阅兼容性后再灰度。
2. 本地受理复用原交易约束。锁定 trace，核对归属、期限、模式和已预扣库存，保存 `PROCESSING`、建单期限和库存阶段。同一个事务保存 eventId、traceId、消息原文、目的地和本地提交证据，避免重复调用另起一个消息身份。
3. Broker 回查按 Key 读取 eventId 对应证据，并核对正文 traceId。存在明确已提交证据时返回 `COMMIT`，即使 trace 已成功或失败。存在针对该消息的确定回滚结果时返回 `ROLLBACK`。事务可能还在执行、记录尚不可见、数据库故障或证据不足时返回 `UNKNOWN`。一笔合法购买终态后是否需要建单仍由现有消费者幂等判定。
4. 发送进度和本地提交证据分别更新。本地事务提交时保存待确认发送进度（例如 `TX_PENDING`）。只有 Broker 的确认或可核实发布结果才能标为 `SENT`，同时记录实际的 `sent_at`。在宽限期内确认缺失时保留待核查状态，超过宽限期转入租约控制的普通 Outbox 重投，仍用原编号和原文。消费者继续按 trace 幂等。

## 死信和灰度

- 死信先按原 eventId 和 traceId 匹配持久化记录。期限内，已确认的旧消息按现有 `SENT` 加 `sent_at` 条件恢复为 `PENDING`。待确认的事务消息走上述确认或重投流程。到期和已有终态沿用当前恢复服务。
- Outbox 转发扫描继续负责发送到期的 `PENDING`。即便 Broker 已收到事务消息，消费者失败之后重新排队仍需要它。订单生命周期事件、延时关单消息、灰度前遗留命令继续由扫描兜底。
- 外层 Agent 确认事务回滚时不能暴露消息或订单事实，先保留现有 Outbox。灰度关闭新路径后，已经进入事务路径的记录继续被回查和恢复。
