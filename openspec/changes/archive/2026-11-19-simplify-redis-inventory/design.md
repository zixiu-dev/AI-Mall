## 数据与状态

同一 SKU 的 `inventory:v1:{skuId}:available` 是 String，`inventory:v1:{skuId}:reservation:<traceId>` 是 Hash。Lua 检查状态和数量后预扣或返还，建单确认只转换预占状态。保留 Redis 调用前写入的恢复意图，数据库建单事务继续条件扣减库存。Redis 丢失已初始化的可售键时停止相关购买，详情返回库存暂不可核实。

接口锁按用户和 trace，MQ 消费标记按 trace。商品布隆过滤器在查询侧使用。同步和异步继续共用库存池，多 SKU 部分失败走原有持久化补偿。

## 部署与对账

旧版本的可售量已经包含未确认预占的扣减，新版本可直接继续处理原预占 Hash。停掉旧版本的库存读写进程后再启动新版，同一库存池禁止新旧混跑。保留 key 前缀与已有数据，新版忽略遗留的 `pending`。回退应先停流并排空库存整理，核对数据库和 Redis 可售量，再按旧版要求恢复每个已初始化库存池的汇总键。发现未完成预占时须先核对具体记录。

基准脚本以数据库 trace 的待处理状态和未完成返还任务来确认整理完成，再对照 Redis 与数据库可售数。未初始化的 SKU 可以没有可售键，已初始化但缺键应判为失败。
