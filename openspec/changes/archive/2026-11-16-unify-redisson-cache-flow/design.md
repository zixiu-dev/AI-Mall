# Redisson 统一访问与缓存流程

## Context

用户关心框架一致性与多实例行为。当前有两套 Redis 连接；MQ 消费去重按用户要求保留，其他公共缓存与交易访问迁到两个具名 RedissonClient，分别连接商品 Redis 和交易 Redis。

## Decisions

- 参数校验仍由业务入口最先执行。L1/Redis 命中无需再查存在性；未命中才查 Bloom，明确否定时不申请任何重建锁、不读数据库、不创建空详情键。
- 去除本机条带锁作为缓存重建互斥入口，用 Redisson RLock 统一跨实例合并；有界等待、锁后双检、每实例回源信号量保留。
- 重建锁采用看门狗续期。回填在同一脚本核对缓存代际与实际锁所有者，失去锁的旧线程不能回填或误解锁。
- RBloomFilter 使用 LongCodec 和新的 v2 键空间，与旧自定义哈希不混读。分批扫描 ID、单调增量补全，合并事务完成前的待登记 ID，并复核数据库 ID；发布就绪状态时检查构建锁，不再复制旧自定义哈希位图。
- 预占多键与路由原子逻辑继续使用 Lua，由 Redisson RScript 执行，不拆成多个网络调用。原库存键/编码/状态保留。
- 商品订阅使用 RTopic，断线重订阅由 Redisson 管理。缓存故障继续有界回源，交易库存故障继续拒绝相关接单。

## Compatibility and Failure

不改 MySQL，不清交易 Redis。新 Bloom 未准备好时放行受保护回源；构建失败不能发布残缺结果。客户端/锁故障不视为不存在。当前按共享单 Redis 的多应用实例验证，不将其宣称为已经验证 Redis Cluster/故障切主。

## Validation

验证非法 ID 在锁前拒绝、本地命中不访问 Bloom、跨独立 Redisson 客户端的重建合并、旧持有者不能回填/解锁、Bloom 构建和未提交注册、丢键及故障放行、库存/routing/MQ原有行为。独立 MySQL + 真实 Redis 全量回归，并以隔离实例验证真实定时 MQ 仍正常。
